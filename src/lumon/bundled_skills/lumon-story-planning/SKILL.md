# 故事规划

这个 Skill 用于在实现开始前，把模糊的业务请求整理成一个可讨论、可验收、
范围明确的 Story。它适用于使用 JIRA 的项目，也适用于没有 JIRA 的纯本地项目。

## 先判断上下文模式

开始提问或写草稿前，读取当前 Workspace 的 `AGENTS.md`，并根据以下证据选择
一种模式。如果存在可访问的 code base，还必须先做与当前请求相关的轻量代码勘察，
再发起澄清访问或写草稿。

### JIRA 模式

仅在用户提供 JIRA Key/URL、`AGENTS.md` 明确要求使用 JIRA/TWG，或 Workspace
已有明确的 JIRA/TWG 配置时进入此模式。
0. 如果未安装 TWG CLI 可进行安装并引导授权登入
1. 使用 TWG CLI 读取完整的 JIRA 上下文：

   ```text
   twg jira workitem get <JIRA-KEY> --full -o json
   ```

2. 结合 TWG CLI 可用的查询命令，探索相关业务背景、评论、链接、附件、历史
   Story、关联工作项和其他项目记录。使用命令前先以当前环境的 `twg --help`
   或对应子命令帮助为准，不猜测未确认的参数。
3. 同时检查当前代码仓的实际代码、配置、测试和 Git 历史，确认业务上下文与
   代码现状之间的关系。
4. JIRA 是业务事实的权威来源；本地代码和 Git 历史是实现现状与历史的证据。
5. 如果明确存在 JIRA 但 TWG CLI 不可用，不得假装已经读取 JIRA。说明缺失的
   证据，并在用户明确同意后，才可以基于用户提供的资料和本地证据继续。

### 独立项目模式

没有上述 JIRA 证据时，不调用 TWG，不要求用户创建 JIRA，也不虚构 JIRA 状态。
使用以下资料完成规划：

- 用户当前提供的目标和业务背景
- Workspace 内的 `AGENTS.md` 和用户明确提供的文档
- 当前代码仓的实际代码、配置、测试和 Git 历史

独立项目模式下，规划草稿保留在当前对话中；只有用户明确要求时，才写入指定的
文档或项目管理系统。

## 基于 Code Base 的访问与分析

只要当前环境存在与请求相关、且可以读取的代码仓，Story Planning 就应先以它作为
实现现状的主要证据。调查范围按请求收敛，不要求无目的地扫描整个组织或所有仓库：

- 先定位相关仓库、入口、用户可见流程、领域模块、配置、测试和近期 Git 历史；同时
  读取 Workspace 的 `AGENTS.md` 与项目级说明。
- 用代码和测试确认当前已经存在的 Actor、行为、边界、错误处理和可观察结果；不要把
  代码里的实现方式直接当成新的业务需求。
- 从“当前实现”和“用户目标 / JIRA 需求”的差异中生成澄清问题。问题前应简要说明
  相关的现状证据，问题本身仍围绕业务目标、行为和验收，不下沉成私有类或函数设计。
- 代码、测试或 Git 历史已经能确认的事实不再询问；只有证据无法确认、且会改变 Story
  范围或验收的问题才交给用户决定。
- 如果没有可访问的 code base，明确标记“缺少代码证据”，再基于用户资料、Workspace
  文档或 JIRA 继续；不得假设当前实现，也不要伪造已经完成代码分析。

## 规划流程

1. 区分已确认事实、合理假设和未解决问题，不把假设写成事实。
2. 先确认目标、主要参与者、业务价值和范围，再确认行为细节。
3. 只询问会改变范围、行为、参与者、权限、时序、失败处理或验收结果的问题。
4. 在形成草稿前执行一次基于现状的澄清访问：尽可能在同一轮列出所有已经识别、且互不依赖的高影响问题；每个问题尽量说明触发它的代码、测试或历史证据。不要为了拆分问题而增加往返。答案互相依赖时，先询问前置问题，收到回答后再进入下一轮。
5. 每个问题都用 A、B、C 列出可选答案，说明每个选项的影响，并在有依据时给出推荐项；允许用户提供自定义答案。例如：

   ```text
   1. <需要确认的问题>
   A. <选项 A>（推荐）
   B. <选项 B>
   C. <选项 C>
   影响：<不同选择会改变什么>
   ```

   用户可以用类似 `1A，2C` 的方式一次回答，也可以直接描述自定义选择。
6. 不重复询问已经被 JIRA、AGENTS.md、代码、测试或 Git 历史明确回答的问题；如果证据已经足够，就不要为了形式而发起访问。
7. 收到回答后，记录已确认决策、保留的假设和仍未解决的问题，再整理 Story；高影响问题未解决时，不把草稿伪装成确定结论。
8. 把需求整理成一个主要业务结果，并用可观察的 Given/When/Then 验收标准描述。
9. 明确记录业务规则、已确认的澄清、依赖、假设和范围外内容。
10. 在进入技术规划前，让用户审阅并明确确认 Story 的业务边界。

## 输出结构

使用用戶提问的语言进行输出，按实际需要包含以下部分：

```markdown
### Background
### Story
### Acceptance Criteria
### Business Rule
### Clarifications
### Out of Scope
```

## JIRA 写入规则

在 JIRA 模式下，规划阶段只读取 JIRA 并在当前会话中形成草稿。只有用户明确
确认后，才可以通过 TWG CLI 写入或更新 JIRA；写入前必须重新读取当前工作项，
确认没有新的人工修改。不得在本地创建一个与 JIRA 自动同步的 Story 镜像。

## 约束

- 这是规划 Skill，不得修改应用源代码、配置或测试。
- 不凭空增加 Actor、数据、集成、权限或业务规则。
- 不把实现细节写入 Story；实现细节留给技术规划。
- 按独立业务结果拆分 Story，不按前端、后端或数据库层强行拆分。
- 没有 JIRA 时保持流程完整，不因为缺少 JIRA 而降低问题澄清和验收标准。
